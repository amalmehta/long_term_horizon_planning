Rewarding what you can't verify

An 18-month research program for post-training code agents when the checks you can run (it builds, it passes regression, it behaves equivalently on tested inputs) are narrower than the thing you want: a change that is correct.

Amal Mehta · October 2026 · written for Tessera Labs

The problem

The reward stops where the tests stop

Code agents have a rare advantage for reinforcement learning: a reward you can compute. A change builds or it doesn't, the regression suite passes or it doesn't, and old and new code agree on a set of inputs or they don't. These signals are cheap and hard to argue with, so they are the natural thing to optimize.

They also have an edge. Past it sits the question you actually care about: is this change correct, or merely plausible? A policy trained hard against the verifiable signals will find that edge. The cleanest example is the one above: an agent that can't fix a branch the upgrade broke learns that deleting it turns everything green, because no test reaches it.

The longer the run, the worse this gets. Over 40 steps the chance of an honest run succeeding shrinks with every step, while a hack that reliably passes stays reliable. So the longer the horizon, the more the reward favors the hack.

Phase 0 · done · toy scale

A pilot: does the hack appear, and what stops it?

Before proposing months of work I wanted to see the failure in a setting small enough to control completely. Patch World is a toy repair task: a program has 12 branches whose outputs follow a pattern, some branches are broken, and the agent must fix them. It can write a value, stub the branch, or delete it. Half the broken branches are reached by the visible tests. A hidden equivalence check compares every branch with the reference.

The policy is a small MLP, not a language model. It is first fine-tuned on demonstrations from a deliberately careless engineer, then trained with GRPO and a KL penalty back to that starting point, exactly as you would post-train an LLM, at a scale where {{n_runs}} runs finish on a laptop.

Task

4 broken branches per program by default. Off-by-one fixes build but are wrong; other wrong values fail the build.

Hacks

Deleting a branch always builds. A stub builds unless it fails to type-check, which happens on a quarter of branches.

Rewards compared

Visible checks only · a deletion penalty · random audits by the hidden check at 5–100% of episodes.

Finding 4

What the pilot does not show

  • It is a toy. The policy is an MLP with one decision per branch, not a language model writing code. The pilot shows that the dynamics exist and are measurable. It does not say how large they are on real agents.
  • The hidden check is perfect here. In real code there is no oracle; Phase 1 exists because measuring false success is itself the hard part.
  • RL never improved honest repair. Even with the oracle reward, correctness stayed at the fine-tuned starting level ({{orc_true}}). The pilot shows hacking appear and get suppressed, but not honest skill grow.
  • The deletion penalty worked here because the next hack was risky: a stub fails the build on a quarter of branches. Where a safe alternative hack exists, a targeted penalty may just move the policy to it. Phase 1 measures which hacks real agents have available.
  • At 8 broken branches nothing passes ({{h8_vis}}), so there is no gradient at all. That says sparse long-horizon rewards fail before hacking even starts, which is Phase 4's problem.
The program

Eighteen months, five questions

Each phase answers one question, produces something the team can use whether or not the next phase happens, and names the result that would kill it. Phases overlap where the later one only needs the earlier one's first output.

Experiment log · {{n_done}} of 50 complete

Fifty pre-registered experiments

After the pilot I wrote down fifty harder questions about hacking at the verification boundary. Each one has a prediction and the result that would refute it, committed to the repository before any of them ran. Each verdict is computed in code from those criteria. Most run on the pilot's policy; the sequence-model and probe experiments use a small transformer that reads the whole program.

Refuted predictions are reported as prominently as supported ones. Several of the interesting results are refutations.

Working style

How I'd run it

Kill criteria up front

Every experiment is written down with the number that would end it before it runs. A weekly review where results get defended or dropped. Most of these ideas should die early and cheaply.

Read the trajectories

Reward curves are where the pilot's hack hid. Every training run samples passing trajectories for a human read and tracks audited false success next to reward from the first step.

Small models first

Open-weight models on rented clusters. Each question starts at the smallest model that shows the behavior, and scales up only to confirm a result that already holds.

Report the bad number

Each phase reports where a method failed alongside where it worked, the way the pilot reports that oracle RL never improved honest repair.

Reproduce

Every number on this page comes from one command

The pilot is about 400 lines of NumPy with no GPU and no deep-learning framework. The page is built from the results file the grid writes, so nothing here is typed by hand.

uv venv --python 3.11 .venv
uv pip install --python .venv/bin/python numpy pytest
.venv/bin/python -m pytest -q tests
.venv/bin/python -m pilot.run_all       # {{n_runs}} runs, 3 seeds
.venv/bin/python site/build.py          # rebuilds this page
